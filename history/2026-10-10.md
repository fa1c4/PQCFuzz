# 2026-10-10 — A-tier public API SOP expansion

## Intent and authority

Expand the 33 A-tier targets from one parameter set and one public call per
target to every public function declared by their primary submitted reference
API headers, across every declared parameter set. The source tree and each
target's own specification PDF supply algorithm-specific context. The design
requirements are `designs/architecture.md` (identity, schema-v2 instances,
candidate-only evidence, DES-01/02/03/06), its linked `specification.md`,
`knowledge.md`, `config.md`, `adapters.md`, `oracles.md`, `mutators.md`, and
`runtime.md`, plus `agent/pqc_sop.md`. The generated claims remain draft and
explicitly distinguish PDF construction context, submitted KAT observations,
cross-backend inference, and locally regenerated KAT observations.

## Implementation

- `scripts/pqcfuzz_a_full_api_inventory.py` inventories declared public
  functions and parameter sets, pins header hashes, and compares registry
  tuples. Its current report is
  `workspace/a_targets_sop/full_public_api_inventory.json`: 52 hash, 343 KEM,
  and 90 signature tuples, 485 unique in total; all 485 have registered
  selectors. The inventory is limited to primary reference headers.
- `scripts/pqcfuzz_a_secondary_probe.py` and
  `scripts/pqcfuzz_a_hash_secondary_probe.py` independently compile and test
  remaining parameter sets against one public KAT vector before registration.
  The asymmetric probe found 46 matches with one missing archived KAT file;
  the hash probe found 36 matches. The four Lore-SM3 builds have their own
  source and KAT provenance. `scripts/pqcfuzz_a_function_probe.py` separately
  qualified the original 17 asymmetric builds' public functions.
- `scripts/pqcfuzz_a_secondary_onboard.py`,
  `scripts/pqcfuzz_a_hash_secondary_onboard.py`, and
  `scripts/pqcfuzz_a_full_api_onboard.py` add exact per-parameter/API config,
  manifest, draft claim, oracle design, adapter, and paired mutator artifacts.
  Their shared implementation lives in `scripts/templates/`; materialized
  target artifacts live under `oracles/<target>/` and the selectors in
  `configs/targets.json`. Each new P1/P2 relation has positive, negative, and
  post-call fault controls. Original 512-bit hash profiles retain P1/P3; other
  hash profiles use P1 on eighteen pinned boundary KAT records.
- The Facto-DSA-512 archive contains a submitted KAT generator but no
  precomputed `Test_Vectors/KAT_SIG_Facto-DSA-512.txt`. Its copied submitted
  generator produced the same 10-record SHA-256
  `192bca21b8e1f83c5a3e31b051eb662853c72709576737daf637e210d58ee5e3`
  on two isolated executions. The reference verifier matched the first
  generated vector. `oracles/sign-10/implement/build.py` regenerates that
  vector under each run's `build/` tree and checks the pinned digest; no
  generated vector is presented as an archived submission file. The
  `generated_kat` capability and claim wording record this distinction.
- `scripts/pqcfuzz_a_full_api_gate.py` runs explicit selector preflight,
  smoke, two campaign iterations, evidence integrity verification, and
  candidate-only checks. `scripts/pqcfuzz_a_finalize_claims.py` reconciles
  expanded document scope and the Facto-DSA-512 provenance label. The earlier
  first-instance `scripts/pqcfuzz_a_soak.py` now explicitly selects the first
  configured instance per target, so the 485-row registry does not break its
  historical 33-target scope.

## Limits and human review

The primary-reference API inventory excludes internal helper functions and
alternate optimized-backend API builds; there is no source/branch coverage
measurement. The short formal gate covers two generated campaign cases per
oracle plus smoke controls; hash P1 uses eighteen selected KAT records, not
every record in each submitted file. Same-lineage vectors and honest
roundtrips provide candidate-only consistency evidence, not independent
normative validation or a computational security proof. Automatic replay and
confirmed-vulnerability promotion remain outside the current architecture.
Human review is still needed to verify each draft PDF claim extraction and to
decide whether internal helpers or alternate backends should be separate SOP
registration scopes. In particular, a human should decide whether the
Facto-DSA-512 locally regenerated KAT is acceptable as a P1 same-lineage
control or whether P1 for that instance should await an archived official
vector or independent reference. Its current draft claim is deliberately
limited to generator/reference self-consistency.
